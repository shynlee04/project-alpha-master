## 📊 MCP Research Findings (Step 2a: Pre-Planning)

### Required Research Questions

**1. What is exact API for FileSystemObserver in Chrome 129+?**

**Answer**: Native API syntax:
```typescript
// Feature detection
if ('FileSystemObserver' in self) {
  // The File System Observer API is supported
}

// Initialize
const observer = new FileSystemObserver(callback);

// Observe file or directory
await observer.observe(fileHandle);
await observer.observe(directoryHandle, { recursive: true });

// Stop observing
observer.disconnect();
observer.unobserve(fileHandle);
```

**Browser Support**: 
- Chrome 129+ (September 11, 2024): Native support
- Chrome 134 (February 26, 2025): Origin trial ends
- Chrome < 129: Fallback to polling required

**2. How to detect browser support for FileSystemObserver?**

**Answer**: Feature detection with `if ('FileSystemObserver' in self)`

**3. Best practices for polling fallback interval?**

**Answer**: Based on research:
- **Recommended interval**: 2000ms (2 seconds) for general file watching
- **Network drives**: 5000ms (5 seconds) due to higher latency
- **Performance vs responsiveness**: 2000-5000ms balances battery usage and responsiveness
- **Source**: File watching libraries (chokidar, watchpack) use 1000-5000ms defaults

**Decision**: Use 2000ms (2 seconds) as default poll interval in `FileWatcher`

**4. Patterns for debouncing file changes?**

**Answer**: Debounce strategies:
- **Duration**: 300-500ms recommended
- **Purpose**: Prevent race conditions from rapid sequential changes
- **Implementation**: `setTimeout` clearing previous timer on new event
- **Aggregation**: Batch events during debounce window to process all at once

**Decision**: Use 500ms debounce (matches story requirements)

**5. Conflict resolution UI patterns?**

**Answer**: Conflict resolution patterns from web research:
- **Dialog-based**: Show modal with 3 options (Keep local, Keep external, Merge, Cancel)
- **Visual diff**: Show side-by-side comparison of changes (old vs new)
- **Context**: Explain what changed (frontmatter vs content vs both)
- **Auto-merge logic**: If only frontmatter changed, simple merge possible
- **Manual merge**: If content changed, show full editor with both versions

**Implementation**: Framework ready (conflict detection via timestamp comparison), but UI hooks not implemented in this story (defers to CC-DF-04)

## 📝 Notes for Future Developers

### Design Decisions Made

1. **Why FileSystemObserver TypeScript workaround?**
   - FileSystemObserver is experimental API (Chrome 129+ only)
   - Not yet in TypeScript @types/node package
   - Workaround: Global interface declaration + `window as any`
   - Alternative: Create local `.d.ts` declaration file
   - Trade-off: Functional code now vs waiting for TS 5.0+ support

2. **Why use 2000ms polling interval?**
   - Based on file watching best practices research
   - Balances battery usage and responsiveness
   - Common in web dev tools (watchpack uses 1000-5000ms)
   - Notes can configure shorter/longer intervals via SyncOptions

3. **Why 500ms debounce?**
   - Prevents race conditions from rapid file changes
   - Standard practice in file watching libraries
   - Allows batching of sequential edits (auto-save in editors)

4. **Why conflict detection via timestamp comparison?**
   - Simple and reliable method for detecting concurrent edits
   - Frontmatter includes `modified` timestamp
   - Compares `file.lastModified > noteMetadata.lastSyncedAt`
   - Can detect external vs local edit conflicts

5. **Why separate FileWatcher and CacheSync?**
   - Clean separation of concerns
   - FileWatcher: File system abstraction (native + polling)
   - CacheSync: Data synchronization logic
   - NoteSyncLayer: Orchestration layer
   - Easier to test and maintain independently

### Performance Considerations

- **Initial Scan**: FileWatcher scans entire directory once on startup
- **Polling**: 2000ms (2 seconds) - reasonable balance
- **Debouncing**: 500ms - prevents UI spam from rapid saves
- **Batch Operations**: CacheSync processes notes in sequence
- **Progress Tracking**: All batch operations support progress callbacks
- **Memory**: No large file content loaded into memory at once (streaming via adapter)
