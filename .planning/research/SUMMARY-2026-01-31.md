# Research Summary: Project Alpha Architecture Redesign

**Domain:** AI-Powered Development IDE with RAG and Agentic Features
**Researched:** 2026-01-31
**Overall Confidence:** MEDIUM-HIGH

---

## Executive Summary

Project Alpha is a client-side AI-powered development environment targeting both desktop (PC with File System Access API) and mobile/tablet (IndexedDB only) platforms. The core architectural challenge is a contaminated codebase with 1,060 "workspace" violations that create entity confusion, plus incomplete Platform Operator implementations (FileTree and Chat-Cascade are stubs or wrongly categorized as plugins).

Research across production systems (LobeChat, ElizaOS, VS Code, OpenCode) reveals a consistent pattern: **operator-module separation** where core infrastructure runs always while optional features plug in. The technology stack (TanStack Start, Zustand v5, Dexie.js, Orama, TanStack AI SDK) is well-chosen but under-integrated. The RAG architecture requires dual-storage: Orama for vectors, Dexie for metadata and relationships.

The key insight from researching Claude artifacts and thread management patterns: **ThreadMessage should use parts-based content blocks** (TextPart, CodePart, ArtifactPart, etc.) rather than simple string content. This enables proper rendering of multi-modal AI responses and tool results.

AI provider strategy should prioritize **Gemini + OpenRouter** as Tier 1 (both OpenAI-compatible APIs) over direct OpenAI due to cost and flexibility considerations.

---

## Key Findings

**Stack:** TanStack Start + Zustand v5 + Dexie.js + Orama + TanStack AI SDK is validated. No changes needed.

**Architecture:** Platform Operators (FileTree, Chat-Cascade) are infrastructure, not plugins. They must be implemented separately from the module system.

**Critical Pitfall:** Dual type system exists (27 files use @/domain/entities, only 2 use @/domain/schemas). Must consolidate to single source of truth in @/domain/schemas/.

**Thread Messages:** Use parts-based content blocks for multi-modal AI responses.

**AI Providers:** Gemini + OpenRouter as Tier 1, both use OpenAI-compatible API patterns.

## Implications for Roadmap

Based on research, suggested phase structure:

### Phase -1: Preparation
**Rationale:** Safety net before destructive changes
- Backup strategy
- Migration planning
- Rollback procedure

### Phase 0: Foundation Cleanup
**Rationale:** Cannot build on poisoned foundation
- Addresses: 1,734 total violations (1,060 workspace + 674 @/lib/)
- Avoids: Building features on incorrect entity relationships

**Tasks:**
- Delete workspace-* type definitions
- Consolidate schemas to @/domain/schemas/
- Update Dexie schema to use projectId only
- Add ESLint rules to prevent regression

### Phase 1: Platform Operators
**Rationale:** FileTree and Chat-Cascade are infrastructure the app IS
- Addresses: FileTree as stub plugin, Chat-Cascade as archived code
- Includes: Layout system recovery (drag-drop fix)

**Tasks:**
- Implement FileTree Operator (project CRUD, file CRUD, sync)
- Implement Chat-Cascade Operator (thread management, AI calls, tool execution)
- Define operator-module boundaries

### Phase 2: AI Integration Layer
**Rationale:** Agentic features require structured tool execution
- Addresses: Tool registry, execution pipeline, multi-provider gateway
- Uses: Centralized AI Gateway pattern (not provider-per-file)

**Tasks:**
- Implement TOOL_REGISTRY (static, code-defined)
- Implement tool execution pipeline with approval workflow
- Integrate TanStack AI SDK with Gemini/OpenRouter
- Implement ThreadMessage with parts-based content

### Phase 3: Feature Modules
**Rationale:** Optional features plug into working platform
- Addresses: Monaco, Notes (with AI features)
- Excludes: Terminal/Preview (moved to Phase 5)

**Tasks:**
- Implement module registration system
- Platform capability detection
- Module-specific UI and state

### Phase 4: RAG System
**Rationale:** RAG requires working file and thread systems
- Addresses: Orama integration, embedding pipeline, thread indexing

**Tasks:**
- Orama per-project instances
- File content indexing
- Thread history indexing
- RAG search integration with Chat-Cascade

### Phase 5: Terminal, Preview & Polish
**Rationale:** WebContainer is complex, isolated at end
- Addresses: Terminal module, Preview module
- Includes: Error handling, testing, UX polish

**Tasks:**
- Terminal module implementation
- Preview module implementation
- Error handling improvements
- Testing coverage
- UX polish

## Phase Ordering Rationale

1. **Preparation (-1)** first because destructive changes need safety nets
2. **Foundation (0)** second because all other phases depend on clean entity model
3. **Platform Operators (1)** third because they ARE the application
4. **AI Integration (2)** fourth because Chat-Cascade needs tool execution
5. **Feature Modules (3)** fifth because they plug INTO working platform
6. **RAG (4)** sixth because it indexes data from all other systems
7. **Terminal/Preview (5)** last because WebContainer is complex and isolated
