# Research Summary: Project Alpha Architecture Remediation

**Domain:** Browser-based IDE with AI capabilities
**Researched:** 2026-01-31
**Updated:** 2026-01-31 (corrected plugin model)
**Overall Confidence:** HIGH

---

## Executive Summary

The current 12-phase roadmap is treating symptoms, not the disease. The root cause of all architectural pain is **conceptual confusion about what the data model should be**.

This research establishes three foundational truths:

1. **Projects OWN data** (files, threads, notes). Workspaces are display modes, not entities. The 361+ references to `WorkspaceBindings` must be eliminated.

2. **Plugins REQUEST writes via Services.** NOT all plugins are passive "lenses":
   - **Core operators** (FileTree, Chat) are ALWAYS loaded and WRITE to storage
   - **Active editors** (Monaco, Notes, Terminal) WRITE via service calls
   - **Passive viewers** (Preview) are true read-only lenses
   
   Services act as gatekeepers enforcing single-writer principle per entity type.

3. **State has 4 layers** with clear boundaries: UI (Zustand no persist) → Session (Zustand + hydration) → Persisted (Dexie) → File (FSA/OPFS). The current state confusion comes from mixing these layers.

Addressing these truths first will make all subsequent phases (imports, store splitting, testing) dramatically easier.

---

## Key Findings

**Stack:** Keep TanStack Start + Zustand + Dexie + TanStack AI SDK. The stack is sound; the architecture isn't.

**Architecture:** 4-layer state model with project-centric ownership. Single source of truth per entity in Dexie. Plugins coordinate via event bus, write via Services.

**Plugin Model (Corrected):**
- FileTree + Chat are **CORE** plugins - always loaded, cannot be disabled
- These provide essential CRUD operations the app depends on
- Other plugins (Monaco, Notes, Terminal) are optional and platform-dependent
- Preview is the only true "lens" (read-only)

**Critical pitfall:** Treating workspaces as entities rather than display modes. This created 361+ workspace references, 6 duplicate FileMetadata types, and 9+ files importing wrong entity sources.

## Additional Research (2026-01-31 Update)

### Plugin Governance

**Problem solved:** "What plugins can load together? What are the limits?"

| Platform | Max Optional | Allowed Plugins |
|----------|--------------|-----------------|
| Desktop | 4 | All 6 plugins |
| Tablet | 2 | FileTree, Chat, Notes only |
| Mobile | 1 | FileTree, Chat, Notes only |

Key governance features:
- **PluginGovernor** class enforces rules at runtime
- Dependency auto-loading (Preview requires Terminal)
- Slot conflict prevention (only one bottom-panel plugin)
- Presets for common configurations (Full IDE, Notes Focus, etc.)

### Schema Architecture

**Problem solved:** "Every plugin has different schema interfaces, not engineered toward relationships."

Solution: **Unified schema layer with plugin extensions**

```
Level 1: Foundation Types (BaseEntity, ProjectOwned, Timestamps)
    ↓
Level 2: Domain Entities (Project, FileMetadata, Thread, Note)
    ↓
Level 3: Plugin Extensions (MonacoFileMetadata, ChatPluginThread, etc.)
```

Key features:
- Zod schemas for runtime validation
- TypeScript types derived from Zod (single source of truth)
- Plugin schema registry for typed extensions
- Schema versioning for backward-compatible evolution

## Implications for Roadmap

Based on research, the 12-phase roadmap should be **consolidated into 6 focused phases** that address root causes, not symptoms:

### Recommended Phase Structure

| Phase | Name | Focus | Why This Order |
|-------|------|-------|----------------|
| **01** | Conceptual Clarity | Domain model, entity ownership, plugin definitions | Nothing else can proceed without clear concepts |
| **02** | Schema Consolidation | Single source of truth for all entities, kill all duplicates | Schemas must be clean before state enforcement |
| **03** | State Layer Enforcement | Zustand/Dexie boundaries, useShallow, useLiveQuery | Clean schemas enable clean state |
| **04** | Plugin Coordination | Event bus, shared state, write locking | Clean state enables plugin coordination |
| **05** | Import & Structure | Kill @/lib/*, canonical paths, god file splitting | Coordination layer enables safe refactoring |
| **06** | Verification & Governance | Tests, lint rules, CI checks | Ensure it stays clean |

### Phase Ordering Rationale

1. **Concepts before code** - Current roadmap jumped to schema changes without establishing what the model should be
2. **Consolidate before enforce** - No point enforcing boundaries if types are duplicated
3. **Coordinate before refactor** - Plugin coordination enables safe parallel work
4. **Verify after stabilize** - Tests on unstable foundations break constantly
