# Domain Pitfalls

**Domain:** AI-Powered Development IDE
**Researched:** 2026-01-31

---

## Critical Pitfalls

Mistakes that cause rewrites or major issues.

### Pitfall 1: Entity Confusion (Workspace vs Project)

**What goes wrong:** Using "workspace" terminology creates entities that don't exist. Files get tagged with workspaceId when they belong to projectId. Queries return wrong results. Permissions apply to wrong scope.

**Why it happens:** Early architecture copied VS Code's "workspace" concept without understanding that VS Code workspaces ARE folders. In browser apps, there's only the project abstraction.

**Consequences:**
- 1,060 violations in current codebase
- Schema relationships broken
- Queries require workarounds
- New features build on wrong foundation

**Prevention:**
- Ban workspaceId, workspaceBindings terminology via ESLint
- Single entity model: Project owns Files, Threads, Notes
- Delete all workspace-* type definitions

**Detection:**
- `grep -rn "workspaceId" src/` returns >0 results
- Entity diagrams show "Workspace" boxes

---

### Pitfall 2: Dual Type Systems

**What goes wrong:** Types defined in multiple locations (@/domain/entities/ AND @/domain/schemas/). Different files import different versions. FileMetadata has 9 different definitions. Updates to one don't propagate.

**Why it happens:** Refactors add new "correct" types but don't delete old ones. Developers don't know which is canonical.

**Consequences:**
- Type mismatches at runtime
- IDE shows wrong property suggestions
- Tests pass with one type, production uses another

**Prevention:**
- Single source of truth: @/domain/schemas/ ONLY
- ESLint rule: `no-restricted-imports` on @/domain/entities/
- Delete @/domain/entities/ directory entirely

**Detection:**
- `grep -rn "from.*entities" src/` returns >0 results
- Same interface name in multiple files

---

### Pitfall 3: Platform Operators Treated as Plugins

**What goes wrong:** FileTree and Chat-Cascade implemented as optional modules. Can be disabled. Have plugin-style registration. Creates confusing boundaries.

**Why it happens:** "Everything is a plugin" sounds clean. But some things ARE the platform, not optional features.

**Consequences:**
- Core functionality can be disabled
- Module boundaries unclear
- Operators don't get special treatment they need
- FileTree stub doesn't work

**Prevention:**
- Explicit separation: Platform Operators vs Feature Modules
- Operators have no "disable" option
- Operators initialize first, before any modules

**Detection:**
- FileTree/Chat-Cascade in plugin registry
- `alwaysLoaded: true` flag on plugins (workaround smell)

---

### Pitfall 4: String-Only AI Messages

**What goes wrong:** ThreadMessage.content is plain string. AI returns mixed content (text, code, artifacts). Parsing breaks. Rendering is wrong.

**Why it happens:** Simple string content is easy to start. Multi-modal responses come later.

**Consequences:**
- Code blocks not syntax highlighted
- Artifacts can't be extracted/rendered
- Tool results mixed with text
- No way to collapse thinking blocks

**Prevention:**
- Parts-based content from day one
- MessagePart union type with explicit block types
- Render pipeline handles each part type

**Detection:**
- `ThreadMessage.content: string` in schema
- String parsing regex for code blocks in render

---

### Pitfall 5: Zustand Persist for Entity Data

**What goes wrong:** Projects, files, threads stored in Zustand with persist middleware. Conflicts with Dexie. No migrations. Stale state after updates.

**Why it happens:** Zustand persist is easy. Dexie requires more setup.

**Consequences:**
- Data duplication (Zustand localStorage + Dexie IndexedDB)
- No schema migrations
- State conflicts on refresh
- Larger storage usage

**Prevention:**
- Zustand for UI state only (panel sizes, modals, active selections)
- Dexie for ALL entity data (projects, files, threads, notes)
- Clear rule: if it has an id, it goes in Dexie

**Detection:**
- `persist(` in store files that handle entities
- localStorage contains project/file data

## Moderate Pitfalls

Mistakes that cause delays or technical debt.

### Pitfall 1: Over-Centralized Stores

**What goes wrong:** God stores >300 lines with unrelated state. Every component re-renders on any change.

**Prevention:**
- Max 300 lines per store (governance check)
- Slices pattern for stores >120 lines
- useShallow for all selectors

---

### Pitfall 2: Direct Storage Access from Modules

**What goes wrong:** Monaco module writes directly to Dexie. No validation, no sync triggers, no audit trail.

**Prevention:**
- All storage via Services (FileService, ThreadService)
- Services handle validation, events, sync
- Modules only call service methods

---

### Pitfall 3: Permission Prompt Fatigue

**What goes wrong:** Every file access asks for permission. Users get frustrated, abandon app.

**Prevention:**
- Request directory permission once
- Persist handle in IndexedDB
- Only re-prompt when handle is revoked

---

### Pitfall 4: Re-Sync on Every Refresh

**What goes wrong:** File tree rebuilds from scratch on browser refresh. Slow, confusing, wastes resources.

**Prevention:**
- Cache metadata in Dexie
- On refresh, validate cache vs file system
- Incremental sync only for changes

---

### Pitfall 5: Monolithic Tool Execution

**What goes wrong:** All tools execute through single synchronous function. Blocking UI, no cancellation, no progress.

**Prevention:**
- Async tool execution with status updates
- Cancellation tokens
- Progress callbacks for long operations
- Queue with concurrency limits

## Minor Pitfalls

Mistakes that cause annoyance but are fixable.

### Pitfall 1: Missing useShallow

**What goes wrong:** Component re-renders when ANY store property changes, even unrelated ones.

**Prevention:**
- ESLint rule requiring useShallow
- Code review checklist item

---

### Pitfall 2: Hardcoded Platform Detection

**What goes wrong:** `if (navigator.userAgent.includes('Mobile'))` breaks on tablets, new devices.

**Prevention:**
- Capability detection: `'showDirectoryPicker' in window`
- Never rely on user agent parsing

---

### Pitfall 3: Unbounded RAG Results

**What goes wrong:** RAG query returns 1000 results. Context window overflow.

**Prevention:**
- Always limit: `search({ limit: 10 })`
- Relevance threshold: `search({ threshold: 0.8 })`

---

### Pitfall 4: Missing Error Boundaries

**What goes wrong:** One component error crashes entire app.

**Prevention:**
- Error boundaries around each module
- Graceful degradation (disable module, show error)
- Error reporting to user

## Phase-Specific Warnings

| Phase Topic | Likely Pitfall | Mitigation |
|-------------|---------------|------------|
| Workspace elimination | Breaking existing code | Incremental: types → infra → UI |
| Platform Operators | Treating as plugins | Explicit operator vs module separation |
| AI Integration | Blocking UI during calls | Streaming responses, async execution |
| Tool execution | No approval workflow | Approval pipeline from day one |
| RAG System | Large index slow | Pagination, relevance threshold |
| Thread compaction | Losing context | Keep old threads in RAG for retrieval |
| Mobile support | Feature parity expectations | Clear platform capability matrix |
