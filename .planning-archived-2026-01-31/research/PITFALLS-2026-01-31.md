# Domain Pitfalls

**Domain:** Browser-based IDE with AI capabilities
**Researched:** 2026-01-31
**Confidence:** HIGH

---

## Critical Pitfalls

Mistakes that cause rewrites or major issues.

---

### Pitfall 1: Treating Workspaces as Entities

**What goes wrong:** Creating workspace IDs, workspace bindings, and workspace-centric schemas when the ACTUAL architecture is project-centric with plugin views.

**Why it happens:** 
- Initial design conflated "display mode" (IDE view vs Notes view) with "data ownership"
- Terms like "workspace" in code editors (VS Code) were adopted without understanding they serve different purposes there

**Consequences:**
- 361+ references to WorkspaceBindings that must be eliminated
- 9+ files importing old entity definitions
- Confusion about which plugins can access which data
- AI agents creating files in wrong locations

**Prevention:**
- **Projects OWN data** (files, threads, notes)
- **Plugins VIEW data** (they are lenses, not owners)
- **Platform DETERMINES capabilities** (what plugins are available)
- Never create an entity for a display concern

**Detection:**
- If you're adding `workspaceId` to a new entity → STOP
- If you're creating a WorkspaceBindings-like structure → STOP
- If a "workspace" is getting its own table in Dexie → STOP

### Pitfall 2: Dual Storage Systems Without Clear Contracts

**What goes wrong:** Having FSA (File System Access) and IndexedDB both storing files without clear rules about which to use when.

**Why it happens:**
- FSA is powerful on desktop but unavailable on mobile
- IndexedDB works everywhere but has different semantics
- Developers add "fallback" logic that becomes primary logic

**Consequences:**
- 2748 filesystem abstraction references creating confusion
- Data sync issues when switching between systems
- Race conditions when both systems try to write
- Users lose data when migration fails

**Prevention:**
- **Decision made at project creation time** (not per-operation)
- **Storage adapter interface** hides implementation
- **Dexie is ALWAYS the metadata source** (file listings, sync status)
- **Content storage is FSA (desktop) or OPFS (fallback)**

```typescript
// CORRECT: Storage type determined at project creation
const project = {
  storageType: hasFileSystemAccess() ? 'fsa' : 'indexeddb',
  directoryHandle: /* FSA handle or null */,
};

// All file operations go through adapter
const adapter = createStorageAdapter(project);
await adapter.writeFile(path, content);  // Adapter knows which system to use
```

**Detection:**
- Direct `showDirectoryPicker()` calls outside project creation → STOP
- Multiple `if (hasFSA) else` branches throughout code → STOP
- IndexedDB and FSA both storing the same file content → STOP

### Pitfall 3: State Duplication Between Zustand and Dexie

**What goes wrong:** Storing the same data in both Zustand (with persist middleware) and Dexie, creating two sources of truth.

**Why it happens:**
- Zustand persist is "easy" for quick persistence
- Dexie requires more setup (schema, migrations)
- Developers add persist "temporarily" and forget to migrate

**Consequences:**
- Data diverges between Zustand localStorage and Dexie IndexedDB
- Sync conflicts on app restart
- Users see stale data
- Hard to debug which source is "correct"

**Prevention:**
- **Rule: Zustand persist is FORBIDDEN for entity data**
- **Dexie is the ONLY persistence layer for entities**
- **Zustand is ONLY for UI state (no persist) and session state (hydrated from Dexie)**

```typescript
// ❌ WRONG: Entity data in Zustand persist
const useProjectStore = create(
  persist((set) => ({
    projects: [],  // This creates a second source of truth!
  }))
);

// ✅ CORRECT: Entity data in Dexie only
function useProjects() {
  return useLiveQuery(() => db.projects.toArray());
}

// ✅ CORRECT: Session state hydrated from Dexie
const useSessionStore = create((set, get) => ({
  activeProjectId: null,
  hydrate: async () => {
    const session = await db.sessions.get('current');
    if (session) set({ activeProjectId: session.activeProjectId });
  },
}));
```

**Detection:**
- `persist()` middleware on a store that contains entity data → STOP
- Same field name in both a Zustand store and Dexie table → STOP
- `localStorage.getItem` for anything except UI preferences → STOP

### Pitfall 4: Plugin Coupling Without Event Bus

**What goes wrong:** Plugins directly calling each other's methods, creating tight coupling and circular dependencies.

**Why it happens:**
- "Just call the other plugin's function" is faster to implement
- Event bus feels like over-engineering for simple cases
- Developers don't see the coupling until it breaks

**Consequences:**
- Circular dependency errors
- Can't load plugins independently
- One plugin change breaks others
- Testing requires mocking entire plugin trees

**Prevention:**
- **Plugins communicate via event bus ONLY**
- **Plugins subscribe to shared state (coordination store)**
- **No direct imports between plugin modules**

```typescript
// ❌ WRONG: Direct coupling
import { monacoPlugin } from '@/plugins/monaco';

function FileTree() {
  const onFileClick = (path) => {
    monacoPlugin.openFile(path);  // Direct call creates coupling
  };
}

// ✅ CORRECT: Event-based decoupling
import { eventBus } from '@/infrastructure/events';

function FileTree() {
  const onFileClick = (path) => {
    eventBus.emit('file:selected', { filePath: path });  // Monaco subscribes
  };
}
```

**Detection:**
- Import from `@/plugins/X` in another plugin → STOP
- Plugin directly calling another plugin's method → STOP
- Plugin holding reference to another plugin → STOP

### Pitfall 5: Safari 7-Day Storage Eviction

**What goes wrong:** Data disappears after 7 days of non-use on Safari/iOS due to Intelligent Tracking Prevention (ITP).

**Why it happens:**
- Safari aggressively evicts IndexedDB data for privacy
- Developers test on Chrome where this doesn't happen
- No persistent storage request in the app

**Consequences:**
- Users lose all project data after 1 week of not using the app
- Impossible to debug (works fine in development)
- User trust destroyed

**Prevention:**
- **Request persistent storage at app start**
- **Document Safari limitations clearly**
- **For critical data: Recommend desktop browsers**

```typescript
// Request persistent storage
async function requestPersistence() {
  if (navigator.storage && navigator.storage.persist) {
    const granted = await navigator.storage.persist();
    if (!granted) {
      console.warn('Persistent storage not granted - data may be evicted');
      // Show user warning about Safari limitations
    }
  }
}

// Check quota
async function checkStorageQuota() {
  const { quota, usage } = await navigator.storage.estimate();
  const percentUsed = (usage / quota) * 100;
  if (percentUsed > 80) {
    // Warn user about storage limits
  }
}
```

**Detection:**
- No `navigator.storage.persist()` call on app start → WARNING
- No storage quota monitoring → WARNING
- Assuming IndexedDB is "permanent" → STOP

## Moderate Pitfalls

Mistakes that cause delays or technical debt.

---

### Pitfall 6: God Stores (>300 LOC)

**What goes wrong:** Single Zustand stores that manage 10+ concerns, making changes cascade unpredictably.

**Prevention:**
- **Max 120 LOC per slice**
- **Use Zustand slices pattern**
- **Split by responsibility, not by entity**

---

### Pitfall 7: Missing `useShallow` on Zustand Selectors

**What goes wrong:** Components re-render on every state change, even for unrelated fields.

**Prevention:**
- **ALWAYS use `useShallow()` when selecting multiple fields**
- **Lint rule to enforce**

```typescript
// ❌ WRONG: Re-renders on ANY store change
const { name, email } = useUserStore(state => ({ name: state.name, email: state.email }));

// ✅ CORRECT: Only re-renders when name or email change
const { name, email } = useUserStore(
  useShallow(state => ({ name: state.name, email: state.email }))
);
```

---

### Pitfall 8: Blocking Main Thread with Large Operations

**What goes wrong:** File tree scanning, embedding generation, or large file reads block the UI.

**Prevention:**
- **Use Web Workers for heavy computation**
- **Stream large files**
- **Virtualize long lists**

```typescript
// ❌ WRONG: Blocks main thread
const embeddings = await generateEmbeddings(allFileContents);  // 10 seconds freeze

// ✅ CORRECT: Worker thread
const worker = new Worker(new URL('./embedding-worker.ts', import.meta.url));
worker.postMessage({ files: allFileContents });
worker.onmessage = (e) => setEmbeddings(e.data);
```

---

### Pitfall 9: No Write Locking for Concurrent Editors

**What goes wrong:** Monaco and Notes both edit the same file, overwriting each other's changes.

**Prevention:**
- **Single writer per file at a time**
- **Debounced writes with lock acquisition**
- **Source attribution on changes**

---

### Pitfall 10: AI Tool Permissions Without Limits

**What goes wrong:** AI agent with file write permission modifies hundreds of files without user approval.

**Prevention:**
- **Suggest mode by default** (agent proposes, user approves)
- **Rate limiting on tool calls**
- **Audit trail for all AI actions**
- **Permission tiers: read-only → suggest → execute**

```typescript
// Tool permission system
interface ToolPermissions {
  read_file: 'always' | 'ask' | 'never';
  write_file: 'suggest' | 'ask' | 'never';  // No 'always' for writes
  execute_command: 'ask' | 'never';
}

// AI must use suggest mode for writes
const writeFile = writeFileDef.server(async ({ path, content }, context) => {
  if (context.permissions.write_file === 'suggest') {
    return { type: 'suggestion', path, content };  // Returns diff, doesn't write
  }
  throw new Error('Write permission denied');
});
```

## Minor Pitfalls

Mistakes that cause annoyance but are fixable.

---

### Pitfall 11: Not Checking Platform Capabilities Before Plugin Load

**Prevention:** Check capabilities at project open, not at feature use.

### Pitfall 12: Mixing Kebab-case and PascalCase in Filenames

**Prevention:** Lint rule enforcing kebab-case for all `.ts` files.

### Pitfall 13: No Dexie Schema Versioning

**Prevention:** Increment version on every schema change, write upgrade functions.
