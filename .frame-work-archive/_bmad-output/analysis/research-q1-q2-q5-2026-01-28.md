## Q1: Nested Project Handling

> "How do we handle users creating projects which are children of another-already-created-project folder?"

### Research Findings

#### VSCode Approach: Multi-Root Workspaces
- **Pattern**: VSCode DOES allow nested folders but with explicit workspace configuration
- **Mechanism**: Multi-root workspaces allow multiple project folders to coexist, but each is treated as a separate root
- **Key Limitation**: Nested `.vscode` folders are NOT supported (GitHub issue #108204, still open)
- **Behavior**: When opening a subfolder, it becomes its own workspace - parent settings are NOT inherited
- **Community Request**: GitHub issue #209613 requests "Nested multi-workspaces" for monorepos - still in backlog

**Source**: [VSCode Multi-root Workspaces Documentation](https://code.visualstudio.com/docs/editing/workspaces/multi-root-workspaces)

#### Obsidian Approach: Strongly Discouraged
- **Official Position**: "The developers strongly advise against any use of nested vaults, warning that the program is not designed to cope with them and things may break"
- **Technical Reason**: Each vault has a hidden `.obsidian` folder for configuration - nested vaults create conflicts
- **Mobile Limitation**: iOS/iPadOS ONLY allows vault root folders directly under the Obsidian folder - no deep nesting
- **Community Workaround**: Multiple config folders pointing to the same shared vault content
- **Key Issue**: Internal links are NOT shared across vaults - each vault is an isolated namespace

**Source**: [Obsidian Forum: Nested Vaults Usage and Risks](https://forum.obsidian.md/t/nested-vaults-usage-and-risks/6360)

#### Notion Approach: Hierarchical But Unified
- Notion uses a single workspace with nested pages/databases
- No concept of "sub-workspaces" - everything exists in one hierarchy
- Simpler model but less flexible for project isolation

### Patterns Identified

| Pattern | Used By | Pros | Cons |
|---------|---------|------|------|
| **Block Nested Projects** | Obsidian | Prevents data corruption, simpler model | Users may accidentally create them |
| **Allow With Warning** | VSCode | Flexibility for power users | Increased complexity, edge cases |
| **Single Hierarchy** | Notion | No nesting issues | Less project isolation |
| **Flatten + Reference** | Git submodules | Clear boundaries | Requires explicit setup |

### Recommendation for Project Alpha

**RECOMMENDED APPROACH: Block + Suggest Migration**

```yaml
strategy: "BLOCK_WITH_DETECTION"

behavior:
  on_project_create:
    - Detect if selected folder is inside existing project
    - If true: Block creation with clear UX message
    - Suggest: "This folder is inside project X. Would you like to:"
      - option_1: "Open existing project X instead"
      - option_2: "Move this folder outside and create new project"
      - option_3: "Create as a subfolder within project X (not a separate project)"
  
  on_project_open:
    - Scan for nested .project-alpha folders
    - If found: Show warning, suggest cleanup
    
  data_model:
    - Project ID is based on root folder path
    - Nested paths are CHILDREN, not separate projects
    - File tree shows hierarchy, not multiple projects
```

**Rationale**:
1. **Obsidian's experience proves** nested vaults cause sync issues and data corruption
2. **VSCode's approach** (allow but unsupported) creates tech support burden
3. **Project Alpha's architecture** (project-centric with plugins) would have ID conflicts with nested projects
4. **Mobile parity** - iOS/Android can't handle nested project structures well

### Edge Cases to Address

| Edge Case | Solution |
|-----------|----------|
| User downloads project into existing project folder | Detection on open, prompt to move |
| Git clone creates nested structure | Detect `.git` + config, offer to promote to project |
| Monorepo with multiple sub-projects | Use "Project Groups" feature (not nested projects) |
| Accidental `.project-alpha` folder duplication | Cleanup wizard, prioritize parent project |

## Q2: Non-PC Feature Parity

> "For NON-PC-USERS... for other features like notion-like-note and knowledge-synthesis and rag-related features... HOW do we manage this?"

### Research Findings

#### How Major Apps Handle Mobile Limitations

**Obsidian Mobile**:
- Full feature parity for core note-taking
- Plugins have mixed support (many desktop-only due to Node.js dependencies)
- Sync works via Obsidian Sync or third-party (iCloud, Git via Working Copy)
- Mobile UI is simplified but functionally equivalent
- **Key Quote**: "Just as good as the desktop app" for markdown editing

**Notion Mobile (2025 Update)**:
- **Offline mode added August 2025** - major milestone
- Limitations:
  - Cannot create new databases offline
  - Cannot access shared workspaces offline
  - Media files don't sync offline
  - Mobile editing limited to pre-opened pages
  - Text-only modifications on mobile per 2025 documentation
- **Architecture**: Uses local cache + sync, not full local-first

**Bear Notes Mobile**:
- Full parity with desktop
- iCloud sync built-in
- No feature restrictions on mobile
- Simpler feature set makes parity easier

### RAG/Knowledge Features on Mobile

**Challenge**: RAG requires vector embeddings (large data) + indexing (compute)

**Strategies**:

1. **Hybrid RAG**: Generate embeddings on server, store locally for search
   - Embeddings: ~768-1536 floats per chunk = 3-6KB per chunk
   - 1000 notes = ~6MB just for embeddings
   - Searchable on-device using HNSW/flat index

2. **On-Demand RAG**: Don't pre-index everything
   - Index only "starred" or "recent" notes
   - Full search requires network for unindexed content
   - Mobile users explicitly choose what to index

3. **Progressive Indexing**: Background indexing with quotas
   - Check `navigator.storage.estimate()` before indexing
   - Pause if approaching 80% quota
   - User controls max storage allocation

### Recommendation

```yaml
mobile_strategy: "TIERED_FEATURES"

tiers:
  essential:
    description: "Core features that MUST work identically"
    features:
      - Note editing (BlockNote)
      - File tree (virtual FS)
      - AI Chat (streamed API)
      - Project switching
      - Search (text-based)
    storage: "IndexedDB"
    
  enhanced:
    description: "Features that work with limitations"
    features:
      - RAG Search (limited to 100 indexed notes)
      - Knowledge synthesis (requires explicit index)
      - Attachments (capped at 100MB total)
    storage: "IndexedDB with quotas"
    user_control: true
    
  desktop_only:
    description: "Features blocked on mobile with clear messaging"
    features:
      - IDE plugins (WebContainer)
      - Full project filesystem access
      - Large file operations
    messaging: "Available on desktop - tap to learn more"

ux_patterns:
  - Show device capability badges in plugin list
  - "Desktop-only" label with explanation
  - Sync status indicator showing what's available offline
  - Storage usage meter in settings
```

**Key UX Principle**: Never silently fail. If a feature isn't available, show WHY and WHAT the user can do (switch to desktop, reduce data, etc.)

## Q5: IndexedDB Limitations

> "As for NON-PC users → finalize of using browserdb → but as issues I have mentioned... I feel this is not enough"

### Research Findings

#### Browser Storage Limits (2026)

| Browser | Storage Quota | Eviction Policy | Notes |
|---------|---------------|-----------------|-------|
| **Chrome (Desktop)** | 60% of disk (up to 600GB on 1TB) | LRU when full | Very generous |
| **Chrome (Mobile)** | 60% of disk | LRU when full | Usually 10-50GB available |
| **Safari (Desktop)** | 10GB best-effort, 250GB persistent | Prompts user | Requires `navigator.storage.persist()` |
| **Safari (Mobile/iOS)** | **50MB Cache API, larger IndexedDB** | **7-day eviction for unused sites** | **Critical limitation** |
| **Firefox** | 10GB best-effort | LRU when full | Reasonable limits |
| **Edge** | Same as Chrome | Same as Chrome | Chromium-based |

**Source**: [MDN Storage Quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

#### Safari iOS - The Critical Problem

**The 7-Day Eviction Rule**:
> "Safari will evict all content from the cache after seven days of Safari use if the user does not interact with the site. This eviction policy **does not apply to installed PWAs** that have been added to the home screen."

**Source**: [web.dev/storage-for-the-web](https://web.dev/articles/storage-for-the-web)

**Implications**:
1. If user doesn't open Project Alpha for 7 days, **ALL DATA IS WIPED** (unless PWA is installed)
2. Even with PWA installed, storage can be evicted under disk pressure
3. IndexedDB quota is more generous than 50MB, but **not guaranteed**

#### Performance for 1000+ Notes

**IndexedDB Performance Characteristics**:
- Read: ~1-10ms per record (single key lookup)
- Bulk read: ~50-200ms for 1000 records
- Write: ~5-20ms per record
- Bulk write: ~100-500ms for 1000 records
- Search: O(n) without index, O(log n) with index

**Practical Experience**:
- Chrome handles 50GB IndexedDB instances efficiently
- V8 heap fragmentation drops 33% vs repeated network hydration
- Loading 200 messages from IDB: 0.4s vs 8.3s from network

**Source**: [Zoho Mail Offline Analysis](https://lifetips.alibaba.com/tech-efficiency/zoho-mail-launches-offers-offline-access-through-gears)

### Alternatives Evaluated

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| **IndexedDB** | Universal support, proven at scale, async API | Safari eviction, no SQL, verbose API | **Use as base layer** |
| **OPFS (Origin Private File System)** | Near-native performance, file-based, persistent | Requires Web Worker for sync API, newer browser support | **Use for SQLite** |
| **SQLite WASM** | Full SQL, ACID, proven reliability, FTS5 | Requires OPFS for persistence, learning curve | **Strong recommendation** |
| **LocalStorage** | Simple API | 5MB limit, sync only, no binary | **Not suitable** |
| **Cache API** | Great for static assets | 50MB limit on iOS, eviction | **For assets only** |

### OPFS + SQLite WASM: The Modern Solution

**Why This Matters**:
> "OPFS is the missing link for the Local-First movement. If you're building developer tools, media editors, or complex offline dashboards, it's time to move beyond the limitations of IndexedDB."

**Architecture Pattern** (from research):
```
┌─────────────────────────────────────────┐
│         Main Thread (UI)                │
│  - Dispatches queries                   │
│  - Receives result sets                 │
│  - 60fps maintained                     │
└───────────────┬─────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────┐
│         Web Worker                      │
│  - SQLite WASM engine                   │
│  - FileSystemSyncAccessHandle (OPFS)    │
│  - ACID transactions                    │
│  - Microsecond latency queries          │
└─────────────────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────┐
│         OPFS Storage                    │
│  - Persistent across sessions           │
│  - Browser-managed file system          │
│  - Not visible to user                  │
│  - LRU eviction only under pressure     │
└─────────────────────────────────────────┘
```

**Browser Support for OPFS**:
- Chrome 86+ ✅
- Edge 86+ ✅
- Firefox 111+ ✅
- Safari 15.2+ ⚠️ (limited, improving)

### Recommendation

**USER'S CONCERN IS VALID. IndexedDB alone is NOT enough for a production-quality local-first app.**

```yaml
storage_strategy: "TIERED_HYBRID"

layers:
  layer_1_sqlite_opfs:
    purpose: "Primary structured data storage"
    technology: "SQLite WASM + OPFS"
    content:
      - Notes metadata
      - Project structure
      - RAG embeddings
      - Search indices
    benefits:
      - Full SQL queries
      - ACID transactions
      - Better than IndexedDB performance
      - Proper relational model
    
  layer_2_indexeddb:
    purpose: "Fallback + large binary blobs"
    technology: "IndexedDB via Dexie.js"
    content:
      - Note content (Markdown/HTML)
      - File attachments
      - Sync queue
    benefits:
      - Universal browser support
      - Good for large blobs
      - Dexie simplifies API
    
  layer_3_cache_api:
    purpose: "Static assets only"
    technology: "Service Worker + Cache API"
    content:
      - App shell (HTML, CSS, JS)
      - Fonts, icons
      - Static images
    benefits:
      - Fast app loading
      - Offline app shell

mobile_mitigations:
  safari_eviction:
    - REQUIRE PWA installation for mobile Safari users
    - Show "Add to Home Screen" prompt prominently
    - Explain: "Keep your data safe - install the app"
    - Implement re-sync on first launch after eviction
    
  storage_monitoring:
    - Check `navigator.storage.estimate()` on startup
    - Warn at 80% quota usage
    - Offer cleanup options (delete old projects, clear cache)
    
  sync_priority:
    - Recent notes sync first
    - Large attachments sync last
    - User can prioritize specific projects
```

### Is IndexedDB Enough? Final Verdict

| Criterion | IndexedDB Only | SQLite + OPFS | Verdict |
|-----------|----------------|---------------|---------|
| **1000+ notes performance** | ⚠️ Adequate | ✅ Excellent | SQLite wins |
| **Complex queries** | ❌ Manual joins | ✅ Full SQL | SQLite wins |
| **Safari eviction** | ❌ Same problem | ❌ Same problem | Neither helps |
| **Browser support** | ✅ Universal | ⚠️ 85%+ (OPFS) | IndexedDB wins |
| **Developer experience** | ⚠️ Verbose | ✅ Standard SQL | SQLite wins |
| **Binary data** | ✅ Good | ⚠️ Via blob | IndexedDB wins |

**RECOMMENDATION**: Use **SQLite WASM + OPFS** as primary storage with IndexedDB fallback for:
1. Older browsers without OPFS
2. Large binary attachments
3. Sync queue (temporary data)

**The Safari eviction problem must be solved at the UX layer** (PWA installation prompts, sync recovery, user education).
