## Description

Create a unified ProjectContext provider that loads project data, initializes storage gateway based on storage type, and provides shared state (file tree, chat service) to all plugins. This removes the need for type assertions in plugin-registry and completes the project-centric architecture foundation.

---

## User Story

**As a** plugin system architect,
**I want** a centralized ProjectContext provider that loads project data, initializes storage gateway, and provides shared services to all feature plugins,
**So that** plugins can access project resources without knowing about project loading or storage details, following the unified project-centric architecture from ADR-034.

---

## Acceptance Criteria

### AC1: ProjectContext interface matches ADR-034 specification
**Given:** ADR-034 defines ProjectContext with project, gateway, platform, shared services
**When:** ProjectContext provider creates the context interface
**Then:**
- Contains `project` (Project object)
- Contains `projectId` (string)
- Contains `gateway` (StorageGateway)
- Contains `platform` (PlatformContract)
- Contains `fileTree` (shared FileTreeState)
- Contains `chatService` (shared ChatService)
- Contains `openFile(path: string): void` action
- Contains `saveFile(path: string, content: string): Promise<void>` action
- Contains `refreshFileTree(): Promise<void>` action

### AC2: Provider loads project from Dexie
**Given:** A projectId is provided to provider
**When:** Provider component mounts
**Then:**
- Queries Dexie database for project with matching ID
- Loads complete project object with all properties
- Handles project not found case (shows error or redirect)
- Sets project state in context

### AC3: Provider initializes gateway based on storageType
**Given:** Project object contains storageType ('fsa' | 'indexeddb')
**When:** Provider component mounts with project loaded
**Then:**
- Uses StorageAdapterFactory to create gateway
- Creates FSA adapter for 'fsa' storage type
- Creates Dexie adapter for 'indexeddb' storage type
- Gateway is available in ProjectContext

### AC4: Provider creates shared file tree state
**Given:** Provider has initialized gateway
**When:** File tree service is needed
**Then:**
- Creates FileTreeState using file-tree-store
- Initializes tree with project root
- File tree is accessible via ProjectContext
- Refreshes tree when project changes
- Single file tree instance per project (not per plugin)

### AC5: useProjectContext() hook for plugin consumption
**Given:** ProjectContext provider is mounted with children
**When:** Component calls useProjectContext() hook
**Then:**
- Returns current ProjectContext value
- Provides type-safe access to all context properties
- Throws error if called outside provider (not in React tree)
- Hook is named and exported from use-project-context.ts

### AC6: TypeScript: 0 errors
**Given:** Provider and hook files are implemented
**When:** TypeScript compiler runs
**Then:**
- No TypeScript errors in created files
- No `any` types used (except where documented)
- All types properly imported from domain layer
- All exports properly typed

## Key Decisions

### 1. Single Gateway Instance Per Project (Not Per Plugin)
- Rationale: Efficient resource usage, consistent file access
- Implementation: Create gateway once in provider, share via context
- Benefit: Plugins don't need to manage gateway lifecycle

### 2. Shared File Tree State (One Source of Truth)
- Rationale: Consistent file state across all plugins
- Implementation: FileTreeState managed centrally, not duplicated per plugin
- Benefit: Single file tree view, no sync conflicts

### 3. Shared Chat Service (Unified Across Plugins)
- Rationale: Single chat history, unified tool execution
- Implementation: ChatService created once, shared via context
- Benefit: Plugins see same chat across all workspaces

### 4. Use StorageAdapterFactory (Canonical)
- Rationale: Already implemented in ARCH-B01-ARCH-B04, reuse existing code
- Implementation: Import from `@/infrastructure/filesystem/StorageAdapterFactory`
- Benefit: Consistent adapter creation, tested code reuse

### 5. Remove Type Assertions from Plugin Registry
- Rationale: ProjectContext fully defined, no need for temporary casts
- Implementation: Update plugin-registry.ts to remove `as` assertions
- Benefit: Cleaner code, type safety maintained

## Implementation Notes

1. **Project Loading:** Use useProjectStore to load project from Dexie by ID
2. **Gateway Initialization:** Call StorageAdapterFactory.create(project.storageType)
3. **File Tree State:** Use file-tree-store with Zustand selectors
4. **Error Handling:** Show error UI if project not found, redirect to hub
5. **Loading State:** Show loading spinner during async project load
6. **Cleanup:** Dispose gateway on unmount if needed (FSA handles may need cleanup)
